# 代入感优化方案（2026-11-12，草案）

承接 [2026-11-12-immersion-review.md](2026-11-12-immersion-review.md)。下文中的游戏字段都已在反编译源码 `Probably Stolen\decomp\` 中核对过。

## 0. 架构原则：三层，各管一件事

```
读取模组 (C#)            事件层 game-world.mjs          导演层 (CL / VideoCohost)
只报“事实”      ──►     把事实的变化翻译成“事件”  ──►  决定要不要唤醒、怎么说
scene=dumping_ground     “你出门去垃圾场了”               awake 仲裁、冷却、表情、字数
woundState=6             “重伤，行动受限”                 人设、知识库
```

- **模组只报事实，不做判断**。比如“50 块算不算高价值”“几秒算路过”，这些阈值都放在 JS 里，调参时不用重新编译模组、重新上传工坊。
- **事件层负责“变化”和“去重”**。快照每 2 秒一次，事件层对比前后两次，只在有意义的变化上产出事件，同时处理路过、复读、批量补发。
- **awake 必须有一个统一的仲裁器**。这次新增的地点、受伤、捡到好东西都会触发唤醒，如果各自直接唤醒，很快就会刷屏。由仲裁器统一按优先级和冷却时间来决定。

## 1. 逐条评估你的 8 条

### 1. 玩家位置 `playerLocation` + 变化时唤醒一次 ✅ 采纳，做两点调整
- 模组读 `MapUIManager.Instance.Current?.Id`，结合 `TransitUI` 是否打开，输出 `scene`：`store` / `map` / `dumping_ground` / `commissary` / `dr_jackson` / 模组地点 Id（如 `be_brew_shop_47`）。旧的 `location` 字段保留不动，以兼容 dsh 版。
- **防抖**：在一个地点停留不到 5 秒（比如在地图上快速切换）只记录，不唤醒。日志里 18 分钟进了 3 次博士店，这个场景下就不会再刷屏。
- **只在有意义的转换上唤醒**：出门、回店、第一次进入某个夜间地点。同一晚第 N 次进入同一地点，只在事件文本里标注“又逛回来”，不唤醒。
- 处在夜间地点时，`npc_arrived` 改写成“你走进了 X 的店”，不计为来客。

### 2. 玩家状态 `playerState` ✅ 采纳，游戏里有现成数据
游戏中的 `PlayerStore.healthData`：
| 字段 | 含义 |
|---|---|
| `woundState` 0 | 健康 |
| 1–5 | 轻伤 |
| >5（`IsSeriouslyWounded`） | 重伤，行动受限（游戏原文是 lost mobility） |
| `isWoundStable == false` | 伤情不稳定，每晚有 10% 概率恶化 |
| `isWoundedFresh` | 今晚刚受的伤 |

- 唤醒：受伤的那一刻（拾荒时触发），以及伤情变化（恶化、稳定、痊愈）。这些变化都发生在夜间结算时，游戏会写入 night log，可以直接复用游戏的文案。
- 立绘：新增 `worried`（担心）和 `crying`（哭泣），各做开口和闭口两张，沿用现有 `pet/assets/jingjing/` 的生成流程。哭泣只用于重伤，轻伤用担心，避免情绪过度。
- 关心要适度：轻伤时只说一句，不反复追问；重伤时她会主动提醒，符合人设里的“危急时会提醒”。

### 3. 拾荒捡到高价值物品时唤醒 ✅ 采纳
- 挂钩 `RunStats.OnScavengedItems(List<GameItem>)`，以及 `OnScavengeInjury(major)` 和 `OnScavengeAttempt`。模组已经挂了好几个 `RunStats` 的方法，照着加就行，风险很低。
- 价值用物品的游戏估值来判断，阈值 50 放在 JS 配置里。具体用哪个估值函数（物品品质会影响价值），实现时再核对。
- 表情：开心或期待。同一次外出里，只对价值最高的那一件唤醒，其余物品合并成一句“还捡了 X、Y”。

### 4. 人设修改 ✅ 采纳，但要注意副作用
新人设是“经验丰富、可靠但毒舌、见证过无数店铺的兴起、想看看你能做到哪一步”。
- **好处**：这解决了“我对当铺一无所知，所以不开口”的沉默问题。
- **风险**：“经验丰富”很容易滑向“经营顾问”，也就是现在房租和利润吐槽泛滥的老问题。对策：
  - 把她的经验定位成**眼光和见闻**（见过哪种店是怎么倒的、哪种人靠不住），而不是算账。数字仍然只说实际看到的。
  - 话题上限：房租和利润只在真实事件发生时才谈（交租、亏本成交），平时不主动翻账本。
  - 她的立场是“旁观你能做到哪一步”，而不是“我来教你怎么做”。
- 技术上：`profile` 是 `immutable: true`，所以要升到 version 7，并走 `migrate-template.ts` 迁移，记忆保留。
- 同步修改：知识库删掉“报价、压价、议价台”的写法（见第 2 节的更正）；`season/script.ts` 里的立场“生意经她还没看明白”改为新立场。

### 5. 鲸鲸的“状态”，替换“泡水的书” ✅ 采纳
- 来源已找到：`core/CharacterLife/src/kernel/state.ts:30` 的 `createInitialActivity()` 把“在给一本泡过水的旧书换封皮”写死成了所有角色的默认活动，而鲸鲸的模板没有覆盖它。
- 方案：
  - 内核：`defineTemplate` 新增可选参数 `initialActivity`，未提供时保持现有行为，向后兼容。这属于内核改动，需要走 Codex 审查。
  - 应用层：鲸鲸的活动**跟着游戏场景走**，由事件层写入。例如在店里时是“趴在柜台边看你接客”，你出门时是“挂在你背包外面望风”，打烊后是“在店里数今天的客人”。这样她的状态本身就带有代入感，你也不用手动维护。

### 6. 读取游戏难度 ✅ 采纳，游戏已提供现成的描述
- `Difficulty.Current.id`：`cozy` / `normal` / `hard` / `challenge`，也可能是模组新增的难度。
- **最省事的做法**：游戏有 `Difficulty.GetEffectLines(difficulty)`，会生成本地化的规则说明，例如“出售时零售加价 15%”“出售时无零售加价”“房租每次上涨 5%”。模组直接把这些文本发出来，她就能读到准确的规则，我们不用自己维护一张表。
- 数值部分（`retailMarkup`、`inventorMarkup`、`merchantDiscount` 等）也一起作为 fact 发出，方便她引用。例如在普通难度下，商人收购给 85 折（`merchantDiscount=15`）。这正好能纠正日志里她误以为对方在“压价 15%”的那句台词。
- 难度在一局中途变化时（模组可以修改难度规则），只唤醒一次。

### 7. 回复能在一个对话框里装下 ✅ 采纳，要从两头一起改
- 现状：对话框最多显示 2 行（`presentation-painter.mjs:276` 的 `slice(0, 2)`），超出部分翻页。人设虽然写了“两句以内、四十字以内”，但只是提示词里的软约束，模型经常不遵守。
- 方案：
  - 显示端：对话框扩大到 3 行，并根据实际字号算出每行能放多少字，作为容量上限。
  - 生成端：用容量上限做**硬限制**。超出时优先在句号处截断，不行再要求模型改短重写；不要截在半句话中间。
  - 同时减少数量：同一个批次里的多个事件合并成一次回复，事件层的去重和合并会让唤醒次数自然下降。

### 8. 识别当前对话 NPC 的身份 ✅ 采纳，根因已确认
- 根因：模组在记录每一行对话时，用的是**那一刻**的 `currentClientInstance`（`JingjingWorldBridge.cs:369`）。说话人名字如果是 "Customer"，就被记成 `unknown`，显示为“来客”。读取延迟导致批量补发时，前一位来客的台词就可能被安到下一位身上。
- 方案：
  - 模组为每次来客分配一个 `visitId`，每行对话都绑定 `visitId`、来客名字和 client id，名字不再是 unknown。
  - 事件层按 `visitId` 分组，严格按“来客 A 到店 → A 的台词 → A 离开 → 来客 B 到店”的顺序输出。
  - 同一位来客的重复台词（如“好，听起来正合适”“我又回来了”）标记为“固定台词”，不当作新信息。

## 2. 对上一份报告的更正

游戏里**有议价面板**（`BargainUIManager`），对正在买货或卖货的来客可以：
- 一次性提出打折或加价（按百分比）；
- 勒索（固定 20%）；
- 威胁改造人。

这些行为会影响口碑（`ComputeTradeRepMultipliers`）。但它是一次性选择，没有来回砍价的过程。所以知识库里的“压价、议价台”并非凭空捏造，问题在于她拿不到议价事件，只能脑补。

## 3. 我建议补充的几项

| # | 补充 | 理由 |
|---|---|---|
| A | **议价事件**：挂钩议价面板，上报“你给 X 打了 9 折”“你勒索了 X”“你加价 20%”，以及口碑的变化 | 让她评论真实发生的议价，而不是脑补。勒索和威胁正好是毒舌人设的好素材 |
| B | **昼夜和天数**：`day`、开店、打烊、夜间结算，加上游戏的 night log（伤情、房租、各项费用）作为当晚总结 | 现在她分不清白天和晚上。night log 是游戏现成的“今天发生了什么”，很适合用来写睡前总结 |
| C | **awake 仲裁器**：统一管理优先级和冷却。优先级：重伤 > 高价值物品 > 出门/回店 > 难度变化，并设全局冷却（比如 20 秒内最多唤醒一次） | 8 条里有 4 条新增唤醒，不统一管理一定会刷屏 |
| D | **地点和来客的结构化计数**：“这是第几次去四十七酿酒商店”“第几次见这位来客”，由事件层根据状态统计，不依赖模型的记忆 | 日志里“我还是头一回见”是记忆没接上导致的；结构化计数可靠得多 |
| E | **知识库重写**：按实际玩法写（批发收购、上架、生产出售、议价面板、拾荒、夜间地点），删掉利润和房租相关的钩子 | 和人设修改一起做，否则新人设会被旧知识库拉回“账房先生”的路子 |
| F | **回放测试**：用这次 11-08 到 11-10 的日志生成新旧事件流，对比出错率 | VideoCohost 已有 `replay/pipeline.ts`，可以把“四十七换了家店名又来了”这类问题变成回归测试 |

## 4. 建议的实施顺序

1. **模组和事件层**（第 1、2、3、6、8 条和 A、B、D）：这是基础，后面所有改动都依赖这些数据。改动集中在 `JingjingWorldBridge.cs` 和 `game-world.mjs`，完成后交 Codex 审查。
2. **导演层**（第 7 条和 C）：awake 仲裁、字数上限、对话框扩大。
3. **人设、知识库、活动**（第 4、5 条和 E）：包括内核的 `initialActivity` 改动（走 Codex 审查）和 profile 迁移。
4. **立绘**（担心、哭泣）：可以和以上步骤并行。
5. **回放验证**（F）：用旧日志验证，然后上机实测。
